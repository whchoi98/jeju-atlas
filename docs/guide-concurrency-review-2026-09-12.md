# 여러 브라우저의 AI 요청 처리 개선안

2026-09-12 06:39 UTC에 운영 설정·CloudWatch와 당시 코드를 점검했다.
아래는 당시의 진단과 제안 기록이다. 이후 사용자 지시에 따라 앱의 이용 한도를 해제하고
현재·누적 접속 집계를 [운영 배포했다](ai-presence-release-2026-09-12.md).
짧은 대기열은 현재 구현에 포함하지 않았다.

## 확인한 현재 상태

| 항목 | 관측·설정 |
| --- | --- |
| 앱 | `Jeju3dApp`, `jeju-3d:19`, running/desired 2/2 |
| AI 동시 처리 | 모든 ECS 태스크를 합쳐 2개 |
| 사용자 동시 처리 | 같은 서명 세션 사용자당 1개 |
| 일일 한도 | 서비스 전체 30회 |
| 시간당 한도 | 사용자당 5회 |
| 요청 제한 시간 | 90초 |
| 결과 불명 요청의 점유 | 시작 시점으로부터 120초 임대가 만료될 때까지 유지 |
| 최근 1시간 ECS 서비스 CPU 최대 관측 | 5.84% |
| 최근 1시간 ECS 서비스 메모리 최대 관측 | 10.30% |
| 최근 3시간 오류 집계 | `guide_busy` HTTP 429 1건 |

사용률은 CloudWatch `AWS/ECS`의 서비스별 5분 `Maximum` 샘플에서 구한 최대값이다.
Bedrock 모델의 여유 용량이나 앞으로의 동시 처리 성능을 측정한 값은 아니다.
오류 집계에는 검증용 요청에서 발생한 400·403도 포함되므로 일반 사용자 실패율로 계산하지 않았다.

`server/admission.mjs`의 DynamoDB 공용 슬롯이 전체 요청을 제한한다.
ECS 태스크를 늘려도 이 슬롯 수는 늘어나지 않는다.
같은 브라우저 프로필의 여러 탭은 같은 사용자 세션으로 묶일 수 있다.
독립적인 사용자 두 명의 요청은 다른 점유가 없다면 현재 설정에서도 함께 허용된다.
현재 429 코드는 전체 슬롯 초과·사용자 중복·원자적 갱신 충돌을 구별하지 않는다.
확인된 오류 1건이 그중 어느 원인인지는 기존 로그만으로 확정할 수 없다.

## 권장 순서

1. **거절 원인을 분리한다.** 전체 용량, 같은 사용자 진행 중 요청, 같은 대화 충돌,
   모델 제공처 제한을 별도 코드·화면 문구·집계로 표시한다. 요청 본문이나 대화 내용은 로그에 남기지 않는다.
2. **전체 동시 처리를 우선 5개로 검증한다.** 사용자당 1개 제한은 유지하고,
   현재 ECS 2개에서 먼저 부하를 측정한다. 5개는 시작 검증값이며 보장 용량이 아니다.
   AgentCore·Bedrock의 계정 할당량과 카카오 조회의 태스크당 동시 작업 2개 제한도 함께 점검한다.
   현재 코드는 최대 2개만 허용하므로 환경변수만 바꾸면 앱 초기화가 실패한다.
   `server/admission.mjs`, `infra/application.yaml`, `scripts/deploy.py`,
   `infra/production.json`의 검사와 설정을 함께 변경해야 한다.
3. **모델 호출 전에만 짧게 기다린다.** 최대 20–30초 동안 제한된 간격과 지연 분산으로
   다시 입장을 시도하며, 화면에는 ‘요청 대기 중’과 취소를 제공한다.
   대기 수 자체에도 상한을 둔다. 대기만 한 요청은 모델 사용량으로 계산하지 않는다.
   원래 요청 ID를 유지하고, 서버가 모델 호출 전 거절임을 확정한 응답에만 적용한다.
4. **응답 시간과 사용 한도를 함께 검토한다.** 불필요한 도구 반복·과도한 답변 길이를 줄인다.
   서비스 전체 하루 30회는 다중 사용자 운영에서 별도의 제약이므로 운영 예산에 맞춰 따로 정한다.
   느린 실제 모델 응답이나 Bedrock 할당량 문제는 ECS 증설만으로 해결되지 않는다.

이미 모델에 전달된 요청, 응답 도중 끊긴 요청, 결과가 불명확한 요청은 자동으로 재호출하지 않는다.
브라우저가 닫혔다는 이유만으로 원격 추론이 끝났다고 간주하거나 임대를 바로 해제해서도 안 된다.
완료를 확인한 경우 해제하고, 불명확한 결과는 기존 임대·중복 방지 규칙을 유지한다.

## 검증 기준

- 독립 사용자 5명의 스트림이 함께 진행된다.
- 초과 요청은 정해진 시간과 대기 수 안에서 대기·취소·만료된다.
- 같은 사용자의 중복 요청과 같은 요청 ID 재전송이 중복 모델 호출로 이어지지 않는다.
- 배포 중 ECS 두 태스크에서도 전체 동시 한도가 유지된다.
- 대기 전 취소에는 모델 호출이 없고, 대기 시간과 모델 응답 시간이 각각 측정된다.
- 429 원인별 횟수, 입장 대기 p95, 첫 응답 p95, 전체 응답 p95,
  모델 제공처 제한과 ECS CPU·메모리를 보고 다음 용량을 정한다.
